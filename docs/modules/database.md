# Модуль Database

## Назначение

Database module — слой хранения состояния системы. PostgreSQL используется не только как база данных, но и как надёжная очередь задач. Это осознанное решение: PostgreSQL уже есть в инфраструктуре, работает offline, поддерживает транзакции, блокировки и JSONB. Отдельный брокер сообщений не нужен.

Миграция:

```text
db/migrations/001_init.sql
```

Подключение:

```text
netops_automation/core/db.py
```

## Таблица `netops_devices`

Это inventory устройств. Scheduler выбирает из неё targets для задач.

Основные поля:

- `name` — уникальное имя устройства.
- `vendor` — производитель или крупная группа, например `NEC`.
- `model` — модель или семейство.
- `mgmt_ip` — IP для подключения.
- `site` и `region` — эксплуатационная группировка.
- `enabled` — участвует ли устройство в планировании.
- `metadata` — JSONB для доменных полей.

Для PMON поле `metadata.device` хранит тип РРС, например:

```json
{"device": "Pasolink NEO/c"}
```

Это поле пришло из старой логики targets и выбирает профиль PMON.

## Таблица `netops_device_credentials`

Здесь лежат учётные данные к устройствам. Они разделены по назначению: `telnet`, `ssh`, `ftp` и так далее.

Пример:

```sql
INSERT INTO netops_device_credentials (device_id, purpose, username, secret)
VALUES ('...', 'telnet', 'admin', '{"password": "..."}'::jsonb);
```

На текущем этапе секреты лежат в PostgreSQL как JSONB. Это просто и достаточно для первого offline-варианта, но требует ограничить права доступа к БД и backup-файлам.

## Таблица `netops_jobs`

Это очередь. Каждая строка — одна работа, которую должен выполнить worker.

Ключевые поля:

- `job_type` — бизнес-тип задачи.
- `scenario` — ключ сценария.
- `transport` — ключ транспорта.
- `status` — состояние.
- `priority` — приоритет.
- `attempt` и `max_attempts` — попытки.
- `run_after` — когда можно пробовать снова.
- `expires_at` — когда задача теряет смысл.
- `locked_by` и `locked_at` — кто взял задачу.
- `timeout_sec` — timeout выполнения.
- `idempotency_key` — защита от дублей.
- `payload` — входные данные сценария.
- `result` — финальный результат.
- `error_code` и `error_message` — краткая причина ошибки.

Для PMON `expires_at` особенно важен: файлы на РРС живут 7 дней, после этого задача должна стать `SKIPPED`, а не шуметь ошибками.

## Таблица `netops_job_events`

Это журнал событий. Он нужен для расследования: когда задача создана, когда взята worker'ом, почему ушла в retry, когда стала failed или skipped.

`netops_jobs` показывает текущее состояние, а `netops_job_events` показывает историю.

## Таблица `netops_artifacts`

Таблица хранит metadata файлов: путь, размер, checksum, тип artifact. Сами файлы лежат на диске, обычно в `/var/lib/netops/artifacts`.

Такой подход проще для больших бинарных файлов PMON и конфигураций. PostgreSQL хранит ссылки и контрольные суммы, но не превращается в файловое хранилище.

## Индексы

В миграции есть индексы под реальные операции:

- выбор готовых задач;
- поиск зависших `RUNNING`;
- поиск истекающих задач;
- просмотр artifacts по устройству.
