# Модуль Transport Layer

## Назначение

Transport Layer отвечает только за обмен данными с endpoint'ом. Он не должен знать, что такое PMON, какие команды нужны NEC, как валидируется файл, куда сохранить конфигурацию и что писать в БД.

Это один из ключевых архитектурных принципов. Если транспорт начинает понимать бизнес-логику, он быстро становится непереиспользуемым. TFTP должен уметь скачать файл. Telnet должен уметь отправить строку и дождаться prompt. SSH в будущем должен уметь выполнить команду. Всё остальное — задача scenario.

Пакет:

```text
netops_automation/transports/
```

## Registry

Транспорты регистрируются в:

```text
netops_automation/transports/__init__.py
```

Текущие ключи:

- `telnet`
- `ftp`
- `tftp`

Именно эти строки используются в `netops_jobs.transport` и в schedule YAML.

## TFTP Transport

Файл:

```text
netops_automation/transports/tftp.py
```

TFTP нужен для PMON и других файлов, которые оборудование отдаёт через простой TFTP. Старые batch-скрипты использовали Windows `tftp -i`. В Debian-варианте используется `tftp-hpa`:

```bash
tftp -g -r <remote_path> -l <local_path> <host>
```

Transport скачивает во временный файл и заменяет итоговый путь только после успешной загрузки. Это защищает от ситуации, когда старый нормальный файл будет затёрт битым или пустым результатом.

Ошибки TFTP считаются retryable: устройство может быть временно недоступно, сеть может быть нестабильна, файл может появиться позже.

## Telnet Transport

Файл:

```text
netops_automation/transports/telnet.py
```

Telnet нужен для старого оборудования, где нет SSH/API. Первый сценарий — NEC CX2200 backup.

Python 3.13 больше не содержит `telnetlib`, поэтому transport реализован через raw socket. Он умеет:

- подключаться к host/port;
- отправлять строку;
- ждать один из prompt'ов;
- выполнять команду;
- закрывать соединение.

Также transport обрабатывает базовую Telnet negotiation: убирает IAC-команды из потока и отвечает отказом на опции. Это достаточно для простых CLI-сессий.

Ограничения:

- нет полноценной terminal negotiation;
- нет обработки pager'а;
- нет privilege escalation;
- нет интерактивных диалогов с несколькими ветками.

Эти вещи должны добавляться аккуратно, когда появятся реальные устройства и transcript'ы.

## FTP Transport

Файл:

```text
netops_automation/transports/ftp.py
```

FTP transport умеет подключиться и скачать файл. Сейчас он не участвует в первом NEC-сценарии, потому что NEC должен сам сохранить конфиг на заранее настроенный FTP-сервер. Но позже FTP может понадобиться, чтобы забирать созданный файл из FTP-хранилища.

## Будущие транспорты

Планируются:

- `ssh` — команды на Cisco, MikroTik, Linux-based устройствах.
- `http` — REST/API устройства.
- `snmp` — статусы, counters, inventory.
- `sftp` — безопасная передача файлов.

## Правила добавления транспорта

Новый transport должен:

1. Жить в отдельном файле.
2. Бросать `TransportError` при сетевых/protocol ошибках.
3. Не знать vendor/device logic.
4. Иметь короткий понятный API.
5. Быть зарегистрированным в `TRANSPORTS`.

Scenario должен быть единственным местом, где transport превращается в полезную операцию.
