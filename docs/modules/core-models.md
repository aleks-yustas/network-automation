# Модуль Core Models

## Назначение

Модуль моделей задаёт общий язык системы. Все остальные части NetOps Automation работают с задачами, статусами и результатами через одни и те же структуры. Это важно, потому что система должна расширяться: сегодня есть PMON и NEC CX2200, завтра появятся Cisco, MikroTik, UPS, SSH, SNMP и новые обработчики. Если у каждого модуля будет своё представление задачи, архитектура быстро станет набором несовместимых скриптов.

Файл реализации:

```text
netops_automation/core/models.py
```

## Что хранит `Job`

`Job` — это задача, которую worker получил из PostgreSQL. Она не описывает конкретный протокол или конкретного производителя. В ней есть только то, что нужно диспетчеру для запуска:

- какой сценарий выполнить;
- каким транспортом пользоваться;
- для какого устройства выполняется работа;
- какие данные передать в scenario;
- сколько попыток уже было;
- когда можно повторить;
- когда задача устаревает.

Самая важная часть здесь — `payload`. Это JSON-поле, куда scheduler складывает параметры, нужные конкретному сценарию. Например, для PMON там будет `target_date` и `device`, а для Telnet backup — `username`, `password`, prompts и command.

Такой подход выбран намеренно. Ядро не должно знать, что такое `Pasolink NEO/c`, где лежит PMON-файл или какая команда нужна NEC CX2200. Эти знания принадлежат доменным модулям и сценариям.

## Статусы задач

Статусы описывают состояние задачи в очереди:

- `NEW` — задача создана и ещё не выполнялась.
- `RUNNING` — задача взята worker'ом.
- `DONE` — задача успешно завершена.
- `FAILED` — задача завершилась ошибкой и больше не будет повторяться.
- `RETRY` — задача упала, но может быть повторена позже.
- `SKIPPED` — задача пропущена осознанно, например истёк срок полезности.
- `TIMEOUT` — задача зависла в `RUNNING`, попытки закончились.

Статусы хранятся в PostgreSQL как строки, а в Python представлены через `StrEnum`. Это делает SQL читаемым, но оставляет в коде проверяемые значения.

## Что возвращает `ScenarioResult`

`ScenarioResult` — результат выполнения сценария. В нём есть:

- `status` — логический статус результата, например `ok` или `empty`;
- `message` — короткое описание для оператора;
- `data` — байты или текст, если сценарий получил полезные данные;
- `metadata` — структурированные сведения;
- `artifacts` — список файлов, сохранённых processors.

Например, PMON-сценарий возвращает raw bytes файла `.pm`, а в `metadata` кладёт имя файла, дату, remote path, размер и количество записей.

## Архитектурные правила

Core models должны оставаться нейтральными. Нельзя добавлять в `Job` поля вроде `pmon_date`, `cisco_command` или `nec_prompt`. Для этого есть `payload` и `metadata`.

Если появляется новый статус задачи, нужно менять не только enum, но и DB CHECK constraint, Queue Manager, документацию и операционные запросы.

## План развития

В дальнейшем стоит добавить отдельные dataclass-модели для `JobEvent` и `Artifact`. Сейчас эти сущности представлены SQL-строками и словарями. Это нормально для раннего этапа, но typed-модели упростят тесты и расширение processors.
