# Модуль Queue Manager

## Назначение

Queue Manager — центральный модуль системы. Он отвечает за то, чтобы задачи выполнялись надёжно: без дублей, с повторными попытками, с защитой от зависших запусков и с понятным финальным статусом.

Файл реализации:

```text
netops_automation/core/queue.py
```

Почему очередь сделана в PostgreSQL: в инфраструктуре уже есть PostgreSQL, он работает offline, умеет транзакции и row-level locking. Для этой задачи не нужны RabbitMQ, Redis или Kubernetes. Нам нужна простая и предсказуемая очередь внутри уже существующей базы.

## Роль в архитектуре

Scheduler создаёт задачи, но не выполняет их. Worker хочет взять задачу, но не должен сам решать вопросы гонок и повторов. Queue Manager находится между ними и отвечает за состояние.

Поток:

```text
Scheduler -> Queue Manager -> PostgreSQL -> Queue Manager -> Worker
```

## Жизненный цикл задачи

Обычный успешный путь:

```text
NEW -> RUNNING -> DONE
```

Путь с временной ошибкой:

```text
NEW -> RUNNING -> RETRY -> RUNNING -> DONE
```

Путь с окончательной ошибкой:

```text
NEW -> RUNNING -> FAILED
```

Путь для задач, которые устарели:

```text
NEW/RETRY -> SKIPPED
```

Путь для зависших задач:

```text
RUNNING -> RETRY
RUNNING -> TIMEOUT
```

## Как задача берётся в работу

Worker вызывает `lease_next()`. Queue Manager выбирает только готовые задачи:

```sql
status IN ('NEW', 'RETRY')
AND run_after <= now()
AND (expires_at IS NULL OR expires_at > now())
```

Затем используется:

```sql
FOR UPDATE SKIP LOCKED
```

Это важная деталь. Если запущено несколько worker'ов, они не возьмут одну и ту же задачу. Один worker заблокирует строку, остальные её пропустят и возьмут другую.

## Приоритеты

Очередь сортируется так:

```text
priority DESC, run_after ASC, created_at ASC
```

Это значит:

1. Более важные задачи идут раньше.
2. Среди задач одного приоритета раньше выполняется та, у которой раньше наступил `run_after`.
3. Если всё одинаково, сохраняется порядок создания.

## Повторные попытки и backoff

Если ошибка retryable, задача не запускается сразу снова. Queue Manager выставляет новый `run_after` через экспоненциальный backoff:

```text
delay = min(backoff_base_sec * 2^(attempt - 1), backoff_max_sec)
```

Это защищает сеть и оборудование от постоянного долбления при аварии, недоступности РРС или проблеме с маршрутизацией.

## Срок полезности задачи

Некоторые задачи имеют смысл только ограниченное время. PMON на РРС хранится 7 дней. Если за это время файл не скачан, задача больше не полезна.

Для этого есть `expires_at`.

Если задача ждёт в `NEW` или `RETRY`, и `expires_at` уже прошёл, Queue Manager переводит её в:

```text
SKIPPED
```

Это не ошибка оборудования. Это честный статус: задача просрочена.

## Восстановление после перезапуска

Если worker упал во время выполнения, задача может остаться в `RUNNING`. При старте worker вызывает `recover_stale_running()`.

Задача считается зависшей, если:

```text
locked_at + timeout_sec < now()
```

Если попытки ещё есть, задача возвращается в `RETRY`. Если попытки закончились, становится `TIMEOUT`.

## Аудит

Каждый важный переход записывается в `netops_job_events`. Это нужно для эксплуатации. Оператор должен видеть не только финальный `FAILED`, но и историю: когда задача создавалась, сколько раз бралась, почему повторялась.

## План развития

Нужно добавить per-device lock, чтобы случайно не открыть два одновременных Telnet/SSH-сеанса к одному устройству. Для PMON через TFTP это не критично, но для CLI-сценариев важно.

Также нужен admin-инструмент: requeue failed, show queue, explain job.
